# Agent开发相关的概念

## 一.什么是 Agent（智能体）

**概念**：Agent 是一个能**自主完成目标**的 AI 系统。会自己**拆解任务 → 调用工具 → 根据结果调整 → 直到做完**。
**核心公式**：`Agent = 大模型（大脑）+ 工具（手）+ 循环（干活方式）+ 运行时（发动机）`，所以agent

## 二.Agent 的三大核心组件

一个 Agent 跑起来，靠三块骨架：**Runtime**（发动机）、**Loop**（循环）、**Tool Calling**（调用外部能力的机制）。

### (1)Agent Runtime（运行时）
**概念**：负责把整个"思考 → 调用 → 执行 → 反馈"过程**真正跑起来的运行环境**。它管理上下文、调度工具、维护状态、处理异常。

>**我自己的理解**：Runtime 就是 Agent 的**发动机/舞台**。模型只管"想"，runtime 负责"把想的东西落地"——拿到模型的工具调用请求，找到对应的工具函数、执行、把结果塞回给模型。没有它，模型再有想法也"动不了"。

### (2)Agent Loop（智能体循环）
**概念**：Agent 不是一次性出结果，而是不断重复 **"思考 → 行动 → 获取结果 → 再思考"** 这个循环，直到任务完成。

这就是经典的 **ReAct 模式**（Reasoning + Acting，先推理再行动）：

```
用户输入
   ↓
[ LLM 思考：判断下一步做什么 ] ──→ 需要外部能力？
   ↑                                  │
   │                             Tool Calling
   │                                  ↓
[ 结果反馈给 LLM 再思考 ] ◀── [ Runtime 执行工具 ]
   │
   └─ 不需要了 → 输出最终答案
```

### (3)Tool / Function Calling（工具调用）
**概念**：Agent 调用外部能力（API、搜索、数据库、执行代码）的机制。

- **Tool（工具）**：把一个函数"暴露"给 LLM，用**名字 + 描述 + 参数结构**告诉它"你有这个能力可用"。工具就是 Agent 的"手"。
- **Function Calling（函数调用）**：LLM 不再输出纯文字，而是输出一段**结构化调用指令**，runtime 解析后执行真实函数，再把结果返回给模型。

```text
工具定义（给 LLM 看的"说明书"）：
{
  "name": "get_weather",
  "description": "查询某城市的天气",
  "parameters": {
    "type": "object",
    "properties": { "city": { "type": "string" } }
  }
}

LLM 返回的调用指令：
{"name": "get_weather", "arguments": {"city": "北京"}}

Runtime 执行真实函数后返回：
{"temp": 28, "desc": "晴"}
```

## 三.开发框架：LangChain 与 LangGraph

### (1)LangChain
**概念**：目前最流行的 LLM 应用开发框架（Python / JS），把开发 LLM 应用需要的组件都封装好了：模型调用、提示词、记忆、工具、Agent。

**特点**：
- **组件化**：像搭积木一样拼装模型、Prompt、工具。
- **生态大**：各种第三方集成都有现成的。
- **缺点**：封装层太厚，"看不到里面在发生什么"，出问题不好排查，所以很多人调侃它"学一半就想换"。

### (2)LangGraph
**概念**：LangChain 团队出的下一代 Agent 框架，本质是规范agent开发的写法，更可控

**核心思想**：把 Agent 的流程画成一张**图（Graph）**——**节点**（Node）是每一步要做的事，**边**（Edge）是流转规则，**状态**（State）在各节点间共享：

```
  开始
   ↓
[ 节点：LLM 思考 ] ←──────┐
   ↓                      │ 还有工具要调用
[ 节点：执行工具 ] ──→ 继续循环
   ↓
[ 节点：输出结果 ] → 结束
```

## 四.能力封装：Skill（技能）

**概念**：把提示词整合打包，根据需求自行调用，也可以整理困难的开发流进行复用

**和 Tool 的区别**：
| 对比项 | Tool | Skill |
|---|---|---|
| 形态 | 一个可调用的函数 | 一套指令 + 文件的技能包 |
| 触发方式 | LLM 直接调用 | 需要时把内容注入上下文 |
| 用途 | 执行具体操作（查天气、发请求） | 赋予专业领域的"做事的套路"（规范、流程、知识） |
| 例子 | `get_weather()` | "写代码防幻觉"的 skill |


## 五.HTTP调用格式

| 协议/格式 | 是谁的 | 备注 |
|---|---|---|
| OpenAI Chat Completions（/chat/completions） | OpenAI 家的老标准 | 但它是事实上的行业标准——DeepSeek、Kimi、GLM、Qwen、Ollama、vLLM 等几乎全都克隆这个格式。 |
| OpenAI Responses API（/responses） | OpenAI 新版主力 API（2025 起推） | 比 Chat Completions 更"一站式"：对话 + 工具 + 文件检索 + 会话状态都包在一个接口里 |
| Anthropic Messages API（/v1/messages） | Anthropic公司的claude | Claude 原生走这套格式。结构不同：system 单独放、人机消息按 user/assistant 交替、工具用 tool_use/tool_result 块 |
| Google Gemini（generateContent） | Google | 自家格式（contents/parts），但它额外提供"OpenAI 兼容端点"方便别人迁过来 |
