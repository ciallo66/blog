# LangChain

**介绍**：LangChain 是用于开发大模型应用的框架，封装了很多用于智能体开发的工具，便于开发。

相较于原生开发：

| 环节 | 原生开发 | LangChain |
| --- | --- | --- |
| 模型调用 | 手写请求、处理响应 | 统一接口调用 |
| 工具定义 | 手写工具描述和参数结构 | `@tool` 自动生成 |
| 工具注册 | 手动组织工具信息传给模型 | 统一交给 Agent 管理 |
| 工具执行 | 手动解析调用请求、匹配函数、传参 | 框架自动调度执行 |
| Agent 流程 | 手写模型与工具之间的循环 | Agent 自动管理 |
| 消息与状态 | 手动组织消息、维护对话状态 | 消息类型与状态机制 |
| 流式输出 | 手动处理流式响应 | 流式接口 |

本文目前覆盖：工具调用与 RAG。

## 一、工具

`@tool` 负责定义工具；`bind_tools()` 和 `ToolNode` 是手动搭图用的底层组件；`create_agent()` 则是把整套循环建好的上层封装。

```python
from langchain_core.tools import tool
from langchain.agents import create_agent
from langgraph.prebuilt import ToolNode
```

```text
手动搭建（底层组件）
@tool 定义 → bind_tools() 绑定给模型 → 模型返回 Tool Call
          → ToolNode 执行 → 结果回传模型 → 条件边决定是否继续

一键搭建（上层封装）
@tool 定义 → create_agent()  // 内部已包含 bind_tools、ToolNode 和整个循环
```

### 1. `@tool` — 定义工具

- **用法**：装饰器，写在 Python 函数定义的上一行。
- **作用**：从函数名、docstring 和类型注解，自动生成工具的名称、描述和参数 Schema（即原本要手写的工具定义）。
- **注意**：docstring 决定模型知不知道工具用途，类型注解决定参数结构；不写 docstring 就没有描述。名称和描述也可以用 `@tool("name")`、`description=` 覆盖。

### 2. `bind_tools()` — 把工具交给模型

- **用法**：`model.bind_tools(tools)`。
- **作用**：把工具的名称、描述和参数 Schema 转换成模型 API 需要的格式并随请求传给模型，由模型自行决定调不调、调哪个。
- **注意**：模型只返回 **Tool Call（工具名 + 参数）**，不执行工具；执行和后续再调模型要另外处理。

### 3. `ToolNode` — 执行工具（LangGraph）

- **用法**：`from langgraph.prebuilt import ToolNode`，用 `ToolNode(tools)` 作为图中的一个节点。
- **作用**：读取状态里的 Tool Call → 调用对应工具 → 把结果作为 ToolMessage 写回状态。
- **注意**：只负责执行，不负责决定下一步；通常配合条件边，判断有没有 Tool Call，再决定走工具节点还是结束流程。

### 4. `create_agent()` — 自动跑完整个循环

- **用法**：`create_agent(model, tools)` 构建 Agent；`agent.invoke({"messages": [{"role": "user", "content": "..."}]})` 启动，答案取 `result["messages"][-1].content`。
- **作用**：内部自动完成 bind_tools、工具执行和"模型 ↔ 工具"循环，直到模型给出最终答案。
- **注意**：想要一个能直接跑的 Agent 就用它；需要自定义图结构时，再用 `bind_tools()` + `ToolNode` 手动搭。

### 小结：各工具替你接手了哪些手工活

| 工具 | 原生开发要手动做 | 它替你做了 |
| --- | --- | --- |
| `@tool` | 编写工具名称、描述、参数 Schema | 从函数签名和 docstring 自动生成 |
| `bind_tools()` | 把工具定义转成模型 API 格式并拼进请求 | 统一绑定 |
| `ToolNode` | 解析 Tool Call、匹配函数、传参、回传结果 | 在图中自动执行 |
| `create_agent()` | 手写模型与工具的循环及终止判断 | 整个 Agent Loop |

## 二、RAG（检索增强生成）

**为什么需要**：模型本身不知道你的私有或最新数据。RAG 先把相关资料检索出来，再让模型基于这些内容回答。

一句话主线：**Loader → Splitter → Embeddings → VectorStore → Retriever → Prompt → LLM。**

Retriever 只负责"取"，取到的 Document 不会自动变成答案，最后要拼进 Prompt 交给模型生成。在 Agent 里，通常把检索封装成 tool，由模型决定何时调用。

```text
建库：文档 → Loader 加载 → Splitter 切分 → Embeddings 向量化 → VectorStore 存储
查询：问题 → Embeddings 向量化 → Retriever 检索 → 拼进 Prompt → LLM 生成答案
```

### 1. Document Loaders（文档加载器）

**作用**：读取不同格式的文件，统一转换成 `Document` 对象（包含 `page_content` 和 `metadata`）。

**用法**：

```python
from langchain_community.document_loaders import PyPDFLoader

loader = PyPDFLoader("需求文档.pdf")
documents = loader.load()
```

- `PyPDFLoader`：加载 PDF 文件。
- `Docx2txtLoader`：加载 DOCX 文件。
- `TextLoader`：加载 TXT 文件。

**注意**：不同格式通常使用不同的 Loader；`load()` 返回 Document 对象列表。`TextLoader` 读中文文本建议指定 `encoding="utf-8"`，否则可能解码失败。

### 2. Text Splitters（文本分割器）

**作用**：将较长的文档切分成较小的文本块（Chunk），方便后续向量化和检索。

**用法**：

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=50
)

chunks = splitter.split_documents(documents)
```

- `chunk_size`：每个文本块的目标大小（默认按字符数计算）。
- `chunk_overlap`：相邻文本块之间重叠的内容大小。
- `split_documents()`：分割 Document 文档列表。

**注意**：分块大小和重叠范围会影响检索效果，需要根据实际文档调整。中文文档可在 `separators` 中加入 `。！？；`，避免句子被生硬截断。

### 3. Embeddings（文本向量化）

**作用**：将文本转换成向量，使计算机能够通过向量相似度判断文本之间的语义相关性。

**用法**：

```python
from langchain_openai import OpenAIEmbeddings

embeddings = OpenAIEmbeddings(
    model="text-embedding-3-small"
)

vectors = embeddings.embed_documents([
    "这是一段示例文本",
    "这是另一段示例文本"
])

query_vector = embeddings.embed_query("查询内容")
```

- `embed_documents()`：将多段文档转换成向量。
- `embed_query()`：将用户查询转换成向量。

**注意**：建库和查询必须使用同一个 Embedding 模型和维度，换模型就要重建索引。示例用的是 OpenAI 的 embedding 接口；DeepSeek 没有 embedding 接口，需要另选提供方或本地模型。

### 4. Vector Stores（向量存储）

**作用**：存储文本向量及其对应的文档内容，并提供向量相似度检索能力。

**用法**：

```python
from langchain_postgres import PGVector

connection = "postgresql+psycopg://user:password@localhost:5432/mydb"

vector_store = PGVector(
    embeddings=embeddings,
    collection_name="documents",
    connection=connection
)

vector_store.add_documents(chunks)
```

- `add_documents()`：将文档向量化并存入向量数据库。
- 常见方案：PGVector、Chroma、FAISS。

**注意**：PGVector 的连接串要使用 psycopg3（`postgresql+psycopg://`），并确保数据库已启用 pgvector 扩展。重复执行 `add_documents()` 会重复插入，批量导入时传入稳定的 `ids`。

### 5. Retrievers（检索器）

**作用**：根据用户查询，从知识库中检索相关文档，返回匹配的 Document 列表。

**用法**：

```python
retriever = vector_store.as_retriever(
    search_kwargs={"k": 3}
)

results = retriever.invoke("用户查询内容")
```

- `as_retriever()`：将向量存储转换为检索器。
- `k`：返回最相关的文档数量。
- `invoke()`：传入查询内容并执行检索。

**注意**：`k` 越大会召回更多片段，但也会占用更多上下文，需要结合模型的上下文长度调整。

### 6. 生成答案

**作用**：把检索到的 Document 作为上下文拼进 Prompt，交给模型生成答案，完成 RAG 的后半段。

**用法**：用 LCEL 把 `retriever → prompt → model → parser` 串起来（检索结果作为 context 传给 prompt）；也可以把检索封装成 tool 交给 Agent。

**注意**：只做到检索不算完整的 RAG，生成这一步不能省。
